# 虚构项目事实册：只供熟悉项目的模拟候选人使用

这不是标准答案、实际运行记录或评分依据。它为 concise、detailed、inarticulate 三个角色提供相同的项目背景，防止对话中随意编造经历。面试官只能收到公共简历与 JD。

## 共同知识与回答边界

三个角色均能理解 Java 基础、线程池、Spring 事务、MySQL 并发更新、Redis 和 RabbitMQ 的常见机制及取舍。表达风格不同，技术理解设定相同。结合当前题目的公开条件作答；事实册不能覆盖题面另行明确的条件。

没有记录的项目配置、性能数字、事故时间和个人职责不能编造。可以解释一般原理或提出假设方案，但明确区分“项目确实这样做”和“如果让我设计”。不声称自己设计了整个系统，不虚构编译、测试或生产验证成功。

## 订单与库存

- 三个 Java 服务实例访问同一个 MySQL 8 主库，业务表使用 InnoDB，隔离级别为 READ COMMITTED。订单和库存操作共用数据源与 Spring 事务管理器。
- 下单前验证商品存在、数量为正及用户身份。库存预留使用带 `available >= quantity` 条件的原子 UPDATE，并检查影响行数。未更新就拒绝下单。
- 订单创建和库存预留在同一短事务内提交。事务不包含支付平台调用。订单创建失败时库存预留一并回滚。
- `(merchant_id, request_id)` 唯一约束防止同一商户重复创建订单。相同请求重试查询原订单；相同键携带不同请求内容应拒绝，不能当成新的成功订单。
- 最初使用单实例内存去重，扩容后无法跨进程生效。后来使用数据库唯一约束。Redis 中的短期标记只减少重复流量，不承担最终正确性。
- 订单从待支付进入已支付或已取消时，使用带预期状态的条件更新。库存释放与取消状态更新同事务执行，仅状态迁移成功时释放一次。
- 回调处理先校验签名、商户、支付单与金额，记录支付通知标识，再做状态迁移。重复通知不能重复扣款或重复推进。
- 已取消订单的迟到支付通知不能直接改成正常已支付订单；记录异常并交由退款或人工核对流程。本人参与异常记录，没有实现支付平台内部退款流程。

## 消息、缓存与排障

- 订单变化和待发送消息写入同一数据库事务，后台发送任务使用 RabbitMQ publisher confirm。发送成功后再更新发送记录；宕机可能导致重发，因此不宣称恰好一次投递。
- 消费者把消息处理标识和业务更新放在同一数据库事务中，提交后确认消息。唯一约束阻止重复业务副作用；失败进入既有重试与死信处理流程。
- 商品展示数据使用 cache-aside：未命中读取数据库，提交更新后删除缓存。TTL 限制陈旧时间；并发读写及删除失败仍可能产生短暂陈旧，不能把它称为强一致。
- 下单使用数据库库存校验，不使用商品展示缓存判断可售库存。没有宣称 Redis 锁可以替代数据库约束。
- 商户订单列表按商户和时间查询，参与设计过 `(merchant_id, created_at, id)` 索引，用 EXPLAIN 和慢查询记录核对执行计划。没有保存可信的性能提升百分比。
- 排查锁等待时结合事务持续时间、更新顺序与锁等待记录。重试不是所有异常的统一解决办法，先区分业务拒绝、临时失败及结果未知。

## 异步导出

- 任务表存储商户、筛选条件、状态、领取令牌、租约到期时间和结果文件标识；不是仅把任务放在线程池内存中。
- 后台实例以数据库条件更新领取任务，再交给专用有界线程池处理。领取和结果提交各使用短事务，查询数据及文件生成不持有领取事务。
- 工作线程定期续租。失去租约的旧执行者不能提交结果；提交时检查领取令牌和任务状态。服务重启后过期任务可被重新领取。
- 按主键游标分批读取，设定开始时的最大 ID，避免深分页和一次性加载全部数据。该方式不是整段导出的时间点一致快照；产品允许导出期间状态更新产生差异，页面说明这一限制。
- 结果文件先写入本次执行专属位置，成功提交文件标识后才对外可见。未采用文件由清理流程处理，不能让迟到执行覆盖当前结果。
- 创建、查询和下载都验证商户归属，不能仅凭猜到任务 ID 下载其他商户文件。
- 线程池饱和时任务保留在持久层等待后续领取，不声称已经生成文件。导出线程池与在线请求资源隔离。
